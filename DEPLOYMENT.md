# GitHub Pages

Публикация: `.github/workflows/pages.yml`, адрес `/development-modeler/` на домене аккаунта GitHub. Repository variables: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (только publishable/anon key). Сборка `npm run build:pages` выполняется во временной папке и сохраняет результат в `out/`. Рабочий Next.js dev-сервер остаётся без изменений.

Модели хранятся в Supabase, а не в GitHub. Ссылка просмотра: `/development-modeler/shared/?token=…`. Запросы редактирования требуют входа; одобрение и отзыв — в «Поделиться». Применить миграцию 003 к рабочей Supabase. На статическом сайте PDF создаётся через страницу отчёта → Print → Save as PDF, A4 landscape; Excel скачивается напрямую.

На GitHub Free для Pages нужен публичный репозиторий. Это публикует исходники и демонстрационную модель; рабочие финансовые данные и `.env.local` исключены.

# Публикация приложения

GitHub хранит исходный код. Для сайта нужен Node.js/Docker-хостинг; GitHub Pages не запускает серверный PDF-экспорт этого приложения.

## Подготовлено

- Dockerfile: Node 22, Chromium для PDF, запуск без root.
- GitHub Actions: тесты, TypeScript и production build.
- `.env*`, локальные отчёты и зависимости исключены из репозитория.
- Supabase migration `003_model_collaboration.sql`: запросы, одобрение, отзыв доступа к конкретной модели и проверка ревизий.

## Развертывание

1. Применить все ещё не применённые SQL-миграции по порядку. Первые две миграции повторно не запускать.
2. При сборке контейнера задать `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` как build arguments. Только публичный publishable/anon key, не service_role.
3. Порт контейнера — 3000. Если хост задаёт другой `PORT`, установить `REPORT_ORIGIN=http://127.0.0.1:<PORT>`.
4. В Supabase Auth указать HTTPS-адрес сайта как Site URL и разрешённый адрес перенаправления. Проверить регистрацию и подтверждение email.
5. Перенести рабочую модель: в локальном приложении Настройки → скачать JSON-копию для резерва → войти в аккаунт приложения → сохранить модели в облако. На публичном сайте войти тем же аккаунтом → загрузить облачные модели. Данные браузера localhost сами на новый домен не переносятся.
6. На публичном сайте открыть «Поделиться» и создать ссылку. Она действует 7 дней и показывает последнюю облачную версию. Запросы редактирования видны там же; их можно разрешить, отклонить и отозвать.

## Проверка доступа перед использованием

С двумя отдельными тестовыми аккаунтами проверить: анонимный просмотр; невозможность сохранить оригинал без разрешения; запрос второго аккаунта; одобрение первого; сохранение после одобрения; отклонение сохранения после отзыва; недоступность остальных моделей организации второму аккаунту; конфликт при одновременном сохранении устаревшей ревизии. Проверить истечение ссылки.

Кнопка «Создать редактируемую копию» создаёт новый ID и отдельную локальную модель, не меняя оригинал. Для синхронизации копии пользователь входит в свой аккаунт и сохраняет её в своё облачное пространство.

Миграция 003 должна пройти эти проверки на Supabase перед объявлением совместного редактирования готовым к эксплуатации. Локальная проверка TypeScript и unit-тестов не заменяет проверку RLS в живой базе.

## Выполненные локальные проверки

53 unit-теста, TypeScript, production build и `tests/shared-copy.mjs` прошли. Все три SQL-миграции выполнены на изолированной PostgreSQL 16; `tests/sql/collaboration.sql` проверил просмотр по токену, отсутствие доступа к таблицам без разрешения, запрет самоодобрения, доступ ровно к одной модели, сохранение после одобрения, конфликт ревизий, отзыв прав и истечение ссылки. Для воспроизведения создать временный контейнер `modeler-access-test` с PostgreSQL и выполнить `python3 tests/sql/run-isolated.py`; скрипт создаёт тестовую схему auth и не предназначен для рабочей Supabase.
